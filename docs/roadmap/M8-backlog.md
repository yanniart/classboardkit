## 3. M8 후보

원칙(바꾸지 않음): 빌드 없음 · 런타임 의존성 0(필요 시 ADR + 벤더링) · 서버·계정 없음 · **학생 기기 참여 없음** · 누구나 무료 · 노트북+태블릿 · v1 계약 유지(→ 모두 **v1.x minor**).

### 3-A. 실사용 검증·다듬기 — v1.1.0 "교실에서 써 보기"
- 교사 인터뷰·사용 관찰 → 피드백 목록 → 작은 개선 우선순위
- 실기기 QA 8~13절 일괄, 발견 결함 수정, 원어민 번역 반영
- 장점: 유일하게 빠진 성공 지표 해결, 이후 기능 선택의 근거. 단점: 사람·기기 일정에 묶임 (자동화 비중 낮음)

### 3-B. 교실 기능 확장 — 벤치마크 대비 빈 곳 (서버 없이 가능한 것)
| 후보 | 근거 | 난이도·메모 |
|---|---|---|
| **저장된 명단** (반별 명단을 한 번 만들어 랜덤 뽑기·모둠 편성에서 선택) | 벤치마크 "이름 목록"(무료 3개 제한 → 우리는 무제한), 교사 반복 입력 부담 | 중 — 보드 밖 데이터(새 저장 키 or Settings 선택 필드), 백업·공유 정책(명단 제외 기본) 설계 필요 |
| **시간표 / 오늘 일과** 위젯 | 벤치마크 Timetable, 초등 교실 수요 | 중 — 현재 교시 강조(시각 기반), 주간/일간 |
| **웹캠(실물 화상기)** 위젯 | 벤치마크 Webcam, 한국 교실 실물 화상기 대체 | 중 — `getUserMedia` 영상, 좌우 반전·정지 화면, 녹화·전송 없음(소음 측정기와 같은 개인정보 원칙) |
| 달력 | 벤치마크 Calendar | 하 |
| 스티커 / 칭찬 도장 | 벤치마크 Stickers | 하~중 — 자체 그림 필요 |
| 링크(하이퍼링크 카드) | 벤치마크 Hyperlink | 하 — 외부 이동만, 임베드(iframe)는 오프라인·보안 문제로 제외 권장 |
| 화면 위 판서(주석 바) | 벤치마크 annotation | 상 — 캔버스 전체 레이어, 실행 취소 모델과 충돌 검토 |
- 장점: 사용자에게 바로 보이는 가치, 생성기·가이드의 첫 실전 검증(dogfooding). 단점: 범위가 커지기 쉬움 → 2~3개로 제한

### 3-C. 보드 생산성
- 위젯 복제, 정렬·맞춤 가이드(스냅), 여러 위젯 선택·이동, 보드 정렬·폴더(벤치마크 Pro 기능), **위젯별 강조색**(M6 D6 이월), 배경 캐러셀
- 장점: 매일 쓰는 교사의 시간 절약. 단점: 실행 취소·키보드·접근성 범위가 함께 커짐

### 3-D. 기술·기여 기반
- 소리 재생 등 내부 모듈을 공개 모듈로 승격(ADR-0011 예외 3건 축소), E2E 실행 시간 단축·안정화(Pages 503 재시도), CI에서 E2E 일부 실행 검토, 추가 언어(zh·fr·pt·de — 기여 유도)
- 장점: 유지보수·기여 비용 감소. 단점: 사용자에게 보이는 변화 적음

### 권장안 (계획서 작성 시 기본값)
**M8 = 3-A + 3-B 일부 → v1.1.0**: "저장된 명단" + "시간표/오늘 일과" + "웹캠" 3개 중 2~3개, 실기기 QA·번역 반영을 같은 마일스톤 안에서. 새 위젯은 **`tools/new-widget.mjs`로 시작**해 기여 경로를 직접 검증한다. 3-C·3-D는 M9 후보로 남긴다.
- 이유: 성공 지표(실사용) 공백을 메우면서, 교사가 매일 반복하는 일(명단 입력·일과 안내·실물 보여 주기)을 줄인다. 모두 서버·학생 기기 없이 가능하고 v1 계약 안(minor)
- 결정이 필요한 것: 저장된 명단의 저장 위치(새 키 `classboardkit:v1:lists` vs Settings 선택 필드)와 백업·공유 포함 여부 → **ADR-0012 후보**

## 4. 계획서 작성 절차 ("m8 계획서 써줘")

1. 읽기: 이 문서 → `CLAUDE.md` → `ROADMAP.md`("v1 이후") → ADR-0011 → `M7-plan.md`(형식 참고) → 최신 devlog
2. 범위 정하기: 3절 권장안을 기본으로 하되, 사용자가 다른 주제를 말하면 그것을 따른다. 계획에 없는 선택은 권장안(사용자 선호 — 일괄 질문 대신 권장안)
3. `docs/roadmap/M8-plan.md` 작성 — M7-plan과 같은 구조:
   `0. 결정 사항(D1~, 채택/대안/이유 표)` · `1. 시작 전 확인(git·단위·E2E 기준선 m1~m7)` · `2. 공통 규칙(v1 계약 유지, 4개 언어 문구, 접근성, sw-stamp)` · `3. 작업 순서(3-0 기반 → … → 마무리·v1.1.0)` · `4. E2E tools/e2e/m8.mjs` · `5. 완료 기준(DoD)` · `6. 리스크`
4. 함께 갱신: `ROADMAP.md`(개요 표에 M8 행, Phase/절), `CLAUDE.md` "▶ 다음 작업"(M8 착수 절차·"m8 진행해줘" 규칙), 필요한 ADR 초안
5. 커밋은 사용자 요청 시 (`docs: M8 실행 계획 (…, v1.1.0)`), 브랜치는 착수 때 `m8`
